# 项目复盘

## 实际投入

自动化实现、测试和材料生成约 30 分钟；该时间不包含提交者后续的真实模型接入、人工代码审查和 GitHub 最终提交操作。题目建议投入 3 小时，因此剩余时间应优先用于真实模型 Trace、业务规则校对和文档个人化。

## 最难问题

最难的部分不是串联工具，而是同时满足三条边界：时段冲突时给出有用建议、未经确认不改变硬性要求、草稿也不能被描述为已发布。实现中把 `requested_time`、`suggested_time`、`pending_confirmations` 和 `published` 分成独立字段，避免一个模糊状态承担多种含义。

另一个关键问题是重复提交。若时段查询把自己的旧草稿也视为冲突，第二次运行会建议不同时间，随后产生幂等冲突。当前查询会忽略同一 `request_id + asset_id` 的草稿，再由保存工具比较完整负载哈希，兼顾稳定重放和防止静默覆盖。

## 学习收获

- Agent 的价值在于根据工具观察调整动作，但业务安全仍需由工具能力和数据结构共同约束。
- Trace 应保存可审计的动作依据，而不是暴露或伪造模型内部思维过程。
- 离线 Mock 对评审复现很重要，但必须明确其证据边界。
- 明确的失败状态、退出码和步数上限比“尽量成功”更适合审核与排期业务。

## 如果再迭代

1. 使用真实模型执行全部场景，加入动作 schema 校验和一次纠错提示；
2. 增加规则版本号、证据来源及人工豁免记录；
3. 将草稿存储替换为带唯一约束和事务的数据库；
4. 支持素材时长、渠道配额、工作日和跨时区的区间排程；
5. 引入审批令牌，只有明确确认后的草稿才能进入后续发布系统；
6. 增加并发请求、损坏状态文件和模型超时测试。
