# 验收示例

测试输入和预期结果合同已完成。`src/` 已实现；`outputs/` 和 `traces/` 只接受程序实际运行结果，不手工伪造。

## 目录

- `inputs/`：八个可执行场景输入。
- `expected/`：对应的部分匹配断言，文件内统一标记 `evidence_type=expected_not_actual`。
- `outputs/`：待实现 Agent 后由 CLI 实际运行生成。
- `traces/`：待实现 Agent 后由运行时实际记录生成。

## 场景映射

| 编号 | 场景 | 核心验收点 |
|---|---|---|
| 01 | 正常排期 | 审核通过、时段可用、仅保存草稿 |
| 02 | 信息缺失 | 请求补充时长，不查询时段、不保存 |
| 03 | 规则风险 | 返回风险原因并阻断 |
| 04 | 时段冲突 | 保留 18:00，建议 19:00，等待确认 |
| 05 | 重复提交 | 两次执行只保留一份草稿 |
| 06 | 保存失败 | 明确返回失败且不虚报成功 |
| 07 | 执行上限 | 达到上限后返回未完成 |
| 08 | 确认替代时段 | 接受 19:00 后重新查询并保存草稿 |

## 使用边界

`test_controls` 仅供测试驱动器使用，不应直接交给模型，也不属于生产业务请求。保存失败注入和执行上限覆盖应由测试驱动器传给 Mock 工具或 Agent Runtime。

`expected_trace_properties` 只规定必须观察到的业务转折和禁止动作，不限定模型唯一执行路径。最终验收必须使用 `src/` 实际运行后产生的 `outputs/` 与 `traces/`，不能用本目录的预期文件代替。离线 Mock 可验证流程，但不能替代真实 DeepSeek 决策证据。
